## 1. 背景与目标

### 1.1 为什么要做这一轮优化

Daily Canvas 目前已经完成了「能跑通」的最小闭环：注册登录 → 每天发一条 → 时间线浏览 → 随机探索 → 个人中心。
但在实际使用中暴露出两类问题：

1. **产品功能偏薄**：用户一天只能发一条纯文本，发完就没事可做。没有互动、没有收藏、没有回看，
   内容的消费深度只有「刷过去」这一层，留不住人。
2. **「关于 Daily Canvas」信息量太少**：目前只有一个版本号、一段更新说明、几行技术信息，
   既没有产品介绍，也没有历史版本、联系方式、隐私说明、问题自查入口。用户想知道「这是什么 App、我能用它做什么、
   出问题了找谁」时，在这个页面里得不到答案。

### 1.2 本轮目标

| 目标 | 说明 | 衡量方式 |
| --- | --- | --- |
| G1 提升内容生产频率 | 降低「每天只能憋一条长文」的压力，让用户更容易表达 | 人均周创作条数、当日发布率 |
| G2 建立内容消费深度 | 让用户可以互动、收藏、回看，形成再次打开的理由 | 人均互动次数、收藏使用率 |
| G3 补齐「关于」模块 | 让关于页成为产品说明 + 版本中心 + 服务状态 + 反馈入口 | 关于页访问量、更新检查成功率 |
| G4 修复已知隐患 | 隐私泄露、日期边界、并发重复发布等技术债 | 上线后线上核实为 0 |

### 1.3 本轮不做（范围边界）

- 不做社交关系链（互相关注、私信、群组）
- 不做推荐算法，发现页仍以「编辑精选 + 随机 + 标签」为主
- 不做多语言（i18n）与桌面端适配
- 不做付费与会员体系

### 2.2 关键问题诊断

以下问题按严重程度排序，P0 为必须在本轮修掉的缺陷。

| 编号 | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0-1 | **公开接口泄露作者邮箱**。时间线是公开接口，但每条创作都带上了作者的完整用户对象，包含 email | 实测 `GET /api/posts` 返回的 `user` 字段为 `['created_at','email','id','username']`；`schemas.py` 的 `PostResponse.user: UserResponse` 含 email | 任何人无需登录即可批量抓取全部用户邮箱，隐私事故 |
| P0-2 | **「每天一条」按 UTC 计算**。后端容器时区为 UTC，`date.today()` 取的是 UTC 日期 | `docker compose exec backend date` 返回 UTC；`crud.check_user_posted_today` 使用 `date.today()` | 北京时间 00:00–08:00 发布的内容会被算作「昨天」，用户在这段时间无法发布新一天的内容 |
| P0-3 | **数据库没有唯一约束**。每人每天一条只靠应用层查询判断，表上只有普通索引 | `models.py` 的 `DailyPost` 仅有 `Index("idx_user_created", ...)`，无 UniqueConstraint | 并发或重试时可能写入同一天两条创作，破坏产品规则 |
| P0-4 | **时间线无法翻页**。接口支持分页，前端只请求 `page=1&limit=20` | `HomePage.tsx` 的 `getTimeline({ page: 1, limit: 20 })` | 第 21 条以后的内容永远看不到，内容越多越严重 |
| P0-5 | **随机漫步全表排序**。随机取一条用 `ORDER BY random()` | `crud.get_random_post` | 数据量增大后每次请求都会全表扫描排序，接口会明显变慢 |
| P0-6 | **401 一律强制跳登录**。拦截器在收到 401 时无条件清除 token 并跳转 `/login` | `frontend/src/api/request.ts` 响应拦截器 | 浏览公开时间线时若携带了过期 token，会被突然踢到登录页 |
| P0-7 | **Token 7 天不可续期**，过期即登出，需要重新输密码 | `config.py` 的 `ACCESS_TOKEN_EXPIRE_MINUTES = 60*24*7`；无 refresh 接口 | 长期用户每 7 天被强制登出一次 |
| P1-1 | 创作发布后**无法编辑、删除、保存草稿** | 无对应接口与页面入口 | 写错一个字就只能认了，用户不敢认真写 |
| P1-2 | 内容**只支持纯文本**，不能配图 | `ComposePage.tsx` 只有 textarea；后端 `content` 为 Text | 表达形式单一，「画布」的概念没有被体现 |
| P1-3 | **没有任何互动能力**：无点赞、无评论、无收藏 | 无对应表、接口、组件 | 内容消费是单向的，用户没有留下的理由 |
| P1-4 | 探索页**可能连续抽到同一篇**，且没有筛选维度 | `get_random_post` 无排除逻辑；无标签/作者筛选参数 | 体验粗糙，探索感弱 |
| P1-5 | 个人中心**无头像上传、无资料编辑、无成长数据** | `ProfilePage.tsx` 用首字母占位；无更新资料接口 | 个人主页没有归属感 |
| P1-6 | **没有找回密码**，忘记密码即账号作废 | `auth.py` 只有 register / login | 用户流失且无客服手段 |
| P1-7 | 时间线**没有搜索、没有标签筛选、没有作者主页** | `get_timeline` 仅接受 page/limit | 历史内容检索不到 |

> 第一轮安全底座已于 2026-11-06 落地：P0-1（邮箱泄露）、P0-2（时区）、P0-3（每日唯一约束）、

## 3. 产品定位与核心闭环

### 3.1 定位

> **Daily Canvas 是一块每天只留给你一次的画布。**
> 它不追求内容量，而追求「今天你真的写下了点什么」，并且能被人看见、被互动、被自己在日后翻回来。

### 3.2 本轮之后的核心闭环

```
打开 App
  → 看今日精选/我的历史（消费）
  → 写下今天的一段（生产，支持配图/草稿/事后补编辑）
  → 收到点赞与评论（反馈）
  → 收藏别人的表达（沉淀）
  → 月末/年末回看自己的画布（回顾）
  → 再次打开 App
```

当前闭环缺的是**反馈**与**回顾**两环，这也是「功能不够」的根本原因。

## 6. 详细需求

### 6.0 FR-0 缺陷修复（P0，最先做）

#### FR-0.1 修复作者邮箱泄露

- **问题**：公开接口 `GET /api/posts`、`GET /api/posts/{id}` 返回的 `user` 对象包含 `email`。
- **改法**：拆出 `PublicUserResponse`（`id`、`username`、`avatar_url`、`created_at`），
  公开接口只返回它；只有 `/api/auth/me` 这类本人接口才返回带 `email` 的完整 `UserResponse`。
- **验收**：
  - 未登录请求 `GET /api/posts`，响应中不出现 `email` 字段（自动化用例断言）。
  - 全站 grep 确认没有任何公开 schema 引用含 email 的用户模型。

#### FR-0.2 修复「每天一条」的日期基准

- **问题**：后端按容器 UTC 日期判定，与用户所在时区（Asia/Shanghai）不一致。
- **改法**：新增配置 `APP_TIMEZONE`（默认 `Asia/Shanghai`），
  所有「今天」的判定改为按该时区的自然日计算；同时在 API 响应中返回 `posted_today` 与
  `next_available_at`，让前端能明确告诉用户「明天几点可以再发」。
- **验收**：
  - 构造北京时间 00:30、08:30、23:30 三个时刻，行为均按北京时间自然日判定。
  - 前端发布页在已发布时显示「下一次可发布：明天 00:00」。

#### FR-0.3 数据库唯一约束

- **改法**：`daily_posts` 增加 `post_date`（DATE，按 APP_TIMEZONE 计算）字段，
  并加唯一约束 `UNIQUE(user_id, post_date)`；写入冲突时返回 409 与友好文案。
- **验收**：并发发起 10 次发布请求，最终只落库 1 条。

#### FR-0.4 时间线分页与无限滚动

- **改法**：首页改为「首屏 20 条 + 触底自动加载下一页」，直到 `page >= total_pages`。
- **验收**：造 60 条数据，滚动到底可看到第 60 条，无重复、无遗漏。

#### FR-0.5 随机漫步性能

- **改法**：随机漫步改为「按 id 随机起点 + 向后取一条」，
  并支持 `exclude_id` 参数排除上一条，避免连续重复。
- **验收**：造 1 万条数据，随机接口 P95 响应 < 100ms；连续点击 10 次不出现紧邻重复。

#### FR-0.6 401 处理与 Token 续期

- **改法**：401 只在**受保护接口**上触发跳登录；公开接口请求失败不跳转。
  新增 `POST /api/auth/refresh`，Access Token 有效期缩短为 2 小时，
  Refresh Token 有效期 30 天，前端在请求前自动续期。
- **验收**：公开发起 401 不跳页；登录态保持 30 天无需重新输密码。

### 6.1 创作域

#### FR-1 草稿箱与「补写昨天」（P0）

> 作为记录者，我想先写一半存下来，也想补上昨天忘写的，这样不会因为「过了今天就不能写」而放弃。

- 规则：
  - 草稿本地保存（离线可用），登录后可同步到服务端；同一用户保留最近 10 份草稿。
  - **严格保持「每天只能发一条」**：同一用户在同一 `post_date` 只允许存在一条创作，
    无论公开还是私密，任何情况下都不放开。
  - 每条创作归属一个 `post_date`。当天可正常发布；允许**补写最近 3 天**内的任意一天，
    补写规则与当天发布完全一致（仍然一天一条）。
  - 补写的内容在时间线上按 `post_date` 排序展示，并带「补写」标记。
- 验收：
  - 断网状态下输入内容，重新打开 App 内容仍在。
  - 补写 2 天前的日期成功；补写第 4 天前的日期被拒绝并提示「最多可补写最近 3 天」。
  - 对已有创作的日期再次发布（含补写）被拒绝，提示「这一天已经写过了」。

#### FR-2 创作编辑与删除（P0）

> 作为记录者，我想改掉错别字，也想删掉不想留的内容。

- 规则：
  - 仅本人可编辑/删除，权限在服务端校验。
  - **内容编辑**：发布后固定 24 小时内可自由编辑（保留「已编辑」标记）；超过 24 小时不可再改内容。
    窗口从发布时间起算，不因补写而延长。
  - **可见性调整不受时间限制**：无论发布多久，作者都可以随时在「公开」与「仅自己可见」之间切换。
    改「内容」有 24 小时窗口，改「给谁看」没有窗口——这是两件独立的事。
  - 删除为软删除，30 天内可通过邮件/客服恢复，超期物理清理。
- 验收：
  - 他人调用编辑接口返回 403；超过 24 小时调用编辑返回 409 并附原因。
  - 发布 3 天后调用可见性接口可以成功改成「仅自己可见」，再改回「公开」同样成功。
  - 同一时刻对同一条创作：改内容被拒（已超 24 小时），改可见性成功。

#### FR-3 创作配图（P1）

> 作为记录者，我想给今天的话配一张图。

- 规则：单条最多 3 张；单张 ≤5MB；支持 jpg/png/webp/heic；服务端压缩到长边 1600px，
  同时生成缩略图；图片存储路径与访问签名策略见第 8 节。
- 验收：上传 5MB 的 HEIC 可成功，列表页使用缩略图，详情页可点击放大。

#### FR-4 心情标签与自定义标签（P1）

- 规则：保留现有 8 个预置心情；新增「自定义标签」，单条最多 3 个，每个 ≤10 字，
  可被其他用户复用（提供联想输入）。
- 验收：新建标签后可在筛选器中看到并按该标签过滤时间线。

#### FR-20 私密创作（仅自己可见）（P0）

> 作为记录者，有些话我只想写给自己看，不想出现在任何公开的地方。

- 规则：
  - 可见性可在发布时选择，也可在**任意时间**切换（`公开` ↔ `仅自己可见`），不受 24 小时编辑窗口限制。
  - 私密创作**只能被作者本人看到**，且必须从所有公开入口彻底排除：
    时间线、随机漫步、搜索、标签筛选、作者主页、收藏列表、通知、分享卡片。
  - 私密创作**不接受任何他人互动**：不能被点赞、评论、收藏、举报（服务端强制校验，非仅前端隐藏）。
  - 他人访问私密创作的详情接口一律返回 404（而不是 403），避免暴露「这条内容存在」。
  - 在作者自己的视图里，私密创作带「仅自己可见」标记，与公开创作混排展示。
  - 计数口径：私密创作计入本人的「累计创作」与「连续发布天数」，但不计入任何公开展示的统计。
- 验收：
  - 用 A 账号发布一条私密创作，用 B 账号在时间线、搜索、随机漫步、作者主页均看不到。
  - B 账号直接请求该创作 id，返回 404。
  - B 账号调用点赞、评论、收藏接口，返回 404 或 403，且不产生任何数据。
  - 作者本人能在个人画布看到该条并标识「仅自己可见」。
  - 同一作者同一天已发一条私密创作后，当天不能再发公开创作。
  - 把一条 3 天前发布的公开创作改为「仅自己可见」后，其他用户立即看不到，作者本人仍能看到。

### 6.6 「关于 Daily Canvas」重构（重点）

  - 「功能一览」：图标 + 名称 + 一句话说明的网格，覆盖创作、探索、互动、个人画布。

#### FR-13 版本中心与更新日志（P0）

- 规则：
  - 分区展示：当前版本 / 最新版本 / 更新状态（已是最新、可更新、强制更新）。
  - **更新日志归档**：把历史版本的 `releaseNotes` 全部展示（按版本号倒序，默认展开最新一版，其余折叠）。
  - 显示每个版本的版本号、发布时间、安装包体积。

  - 更新操作沿用现有能力：检查更新 → 下载（带进度）→ 安装（带「需要授权」引导）。

#### FR-14 服务状态与自助排查（P0）

  - 接口版本与 App 版本是否匹配
  - 配置来源（远程 / 缓存 / 内置）与配置更新时间
  - 一键「重新检测」「重新拉取服务器地址」「清理本地缓存」
- 验收：
  - 隧道失效时，检测结果明确显示「服务器不可达」并给出「重新拉取地址」按钮。
  - 点击「重新拉取服务器地址」后，若配置更新成功，登录接口恢复正常。
  - 「清理本地缓存」只清缓存，不清登录态。

#### FR-15 反馈与联系（P0）

> 作为用户，我想反馈问题，并希望反馈时自动带上排查信息。

- 规则：

    - 后台支持按状态、类型、时间筛选，支持标记「重复工单」并合并。
    - 管理端入口受权限保护，不对外开放（沿用 FR-17 的管理能力）。
- 验收：
  - 提交反馈后能在「我的反馈」看到记录、受理编号与当前状态。
  - 后台回复后，用户端能看到回复内容与时间。
  - 用户追加补充后，工单在原编号下更新，不新建工单。

### 6.7 内容安全与用户保护

设计原则：**用户侧自助（拉黑）+ 平台侧处置（举报）+ 发布前预检（敏感词）** 三层互补。
只做举报是事后兜底，用户在看到不适内容时仍会被持续打扰；只做拉黑则违规内容仍在公共池里扩散。

#### FR-17 举报与审核处理（P0）

> 作为用户，我看到不健康的内容时，能一键举报，并且知道平台会真的处理。

- 规则：
  - **举报入口**：时间线创作卡片、创作详情页、作者主页、评论区（FR-6 上线后）均提供「举报」。
    移动端用长按或右上角菜单触发，避免破坏留白版式。
  - **理由分类**：色情低俗、暴力血腥、辱骂攻击、广告引流、违法违规、侵犯版权、其他。
    选择「其他」时可补充文字说明（≤200 字）。
  - **一键拉黑**：举报弹层内提供「同时拉黑该作者」勾选项，默认勾选，一次操作解决「举报 + 不再看到」。
  - **防滥用**：同一用户对同一对象只能举报一次；单用户 24 小时内举报上限 20 次；
    超限返回明确提示，不静默失败。
  - **自动降级**：同一条内容被 ≥5 名不同用户举报时，自动把创作状态置为「审核中」（`pending`）并从公开列表暂时隐藏，
    人工复核后「恢复」或「确认违规」。这条规则用于阻断扩散，避免等到人工处理时已经传开。
  - **状态可见**：用户可在「我的举报」看到受理编号与状态：待处理 / 处理中 / 已处理 / 不予处理。
  - **处置动作**：忽略、隐藏内容、删除内容、警告作者、封禁账号。
    作者侧提示：隐藏显示「该内容因违反规范已被隐藏」；删除显示「内容已移除」；封禁显示剩余天数与申诉入口。
  - **管理端**：与 FR-15 的反馈工单**复用同一套 staff 管理端**（`staff_users` 权限体系），
    举报队列按对象聚合（同一对象的多条举报合并展示），支持按理由、时间、被举报次数排序。
  - **处置留痕**：每次处置记录处置人、时间、动作、备注，可追溯（`moderation_actions`）。
- 验收：
  - 举报后管理端能看到记录，且同一对象的多次举报被聚合为一条，显示举报次数。
  - 隐藏内容后，公开列表、搜索、随机漫步、作者主页都不再返回该内容。
  - 第 5 个不同用户举报同一条内容时，该内容自动从公开列表消失并进入待审。
  - 同一用户重复举报同一内容，第二次返回「你已举报过该内容」，不产生重复记录。
  - 「我的举报」能看到受理编号与状态流转。

#### FR-21 拉黑与屏蔽（P0）

> 作为用户，我不想再看到某个人的内容，也不想被他继续打扰。

- 规则：
  - **入口**：创作卡片菜单、作者主页、评论区（FR-6 上线后）提供「拉黑」；个人中心提供「已拉黑」管理页。
  - **关系模型**：拉黑是单向记录（只有 A→B 一条），但**效果双向隔离**。这样被拉黑的人无法换个方式继续骚扰。
  - **A 拉黑 B 之后，生效范围**：
    - A 的时间线、搜索、随机漫步、收藏列表中不再出现 B 的公开创作
    - **B 也看不到 A 的公开创作**（时间线、搜索、随机漫步、作者主页）
    - 双方无法对彼此的创作点赞、评论、收藏（服务端强制校验）
    - 双方不再互相产生任何通知
    - B 访问 A 的作者主页返回 404，不暴露「你被拉黑」这一事实，避免激化冲突
  - **解除拉黑**：立即恢复全部可见性与互动能力，无需重新登录。
  - **上限与防滥用**：单个用户最多拉黑 1000 人；不影响举报记录与后台处置结果。
  - **幂等**：重复拉黑、重复解除均返回成功，不报错。
  - **不误伤**：拉黑只影响「双方之间的可见性与互动」，不影响被拉黑者对其他人的正常使用。
- 验收：
  - A 拉黑 B 后，A 的列表中看不到 B；用 B 账号登录，也看不到 A。
  - B 直接请求 A 的创作 id 与作者主页，返回 404。
  - B 调用点赞 / 评论 / 收藏接口，返回 403 且不产生数据。
  - A 解除拉黑 B 后，双方立即可见、可互动。
  - 拉黑关系只写一条记录，重复调用不产生重复数据。

#### FR-22 敏感词发布前校验（P2，可选）

> 作为平台方，希望在内容发出去之前就拦住明显违规的内容。

- 规则：
  - 维护一份可配置的敏感词库（高危词 / 疑似词），发布与编辑时做本地匹配。
  - 命中高危词：直接拒绝发布并提示「内容包含不允许的表述，请修改后再发布」。
  - 命中疑似词：允许发布但标记为「待审」，进入人工队列（不自动公开到精选位）。
  - 不做 AI 语义审核，先做词库 + 人工复核，避免误判和额外依赖。
- 验收：含高危词的创作无法发布；含疑似词的创作发布后进入待审队列。

#### FR-23 创作状态机（每条创作都有明确状态）（P0）

> 作为产品方，我需要一眼看出每一条创作现在是什么状态：是正常、只有作者能看、正在审核、已被隐藏，还是已被删除。
> 状态不能靠零散的布尔字段拼出来，必须是**一条创作一个明确状态**，并且每次变化都有记录。

- **两条正交的轴，不要混成一个字段**：

  | 轴 | 字段 | 取值 | 含义 |
  | --- | --- | --- | --- |
  | 作者意图 | `visibility` | `public` / `private` | 这条内容作者想给谁看 |
  | 平台裁定 | `status` | `normal` / `pending` / `hidden` / `deleted` | 这条内容有没有审核问题 |

  两者正交组合，收益是「作者把内容设为仅自己可见」不会被误当成「审核状态」，
  「平台隐藏」也不会覆盖作者原本的可见性设置（恢复时可以还原成原来的可见性）。

- **`visibility` 的取值与归属（作者自己的意愿）**：

  | 取值 | 含义 | 谁能改 | 什么时候能改 |
  | --- | --- | --- | --- |
  | `public` | 公开，所有人可见 | 作者 | 发布时默认；之后**任意时间**都可改 |
  | `private` | 仅自己可见 | 作者 | 同上 |

- **`status` 的取值与归属（谁有权设成这个状态）**：

  | 取值 | 含义 | 谁能设置成这个状态 |
  | --- | --- | --- |
  | `normal` | 正常，没有审核问题 | **系统**：发布成功时默认置入。**管理员**：复核通过或误判恢复时置入 |
  | `pending` | 审核中，暂不公开 | **系统**：被 ≥5 名不同用户举报，或命中疑似敏感词时自动置入。**管理员**：也可手动置入 |
  | `hidden` | 已确认违规，已隐藏 | **仅管理员** |
  | `deleted` | 已删除 | **作者**：主动删除。**管理员**：严重违规强制移除 |

  一句话记牢：**四个状态里只有 `deleted` 是作者自己能设的**，
  `normal` 是发布时的默认值（之后只有管理员能恢复回来），`pending` 由系统自动触发，`hidden` 只有管理员能动。

- **展示层对用户呈现为 5 种状态**（接口返回 `status` 与 `visibility`，前端展示为下列之一）：

  | 展示状态 | 条件 | 谁能看到 | 在作者侧的表现 |
  | --- | --- | --- | --- |
  | 正常 | `normal` + `public` | 所有人 | 无徽标或灰色「公开」徽标 |
  | 仅自己可见 | `normal` + `private` | 仅作者 | 「仅自己可见」徽标 |
  | 审核中 | `pending` | 仅作者 | 「审核中」徽标 + 说明 |
  | 已隐藏 | `hidden` | 仅作者 | 「已违反规范，已被隐藏」徽标 + 申诉入口 |
  | 已删除 | `deleted` | 作者可在回收站看到（30 天内） | 回收站中可见，可恢复 |

- **`visibility` 流转（作者操作，两条轴里的「作者轴」）**：

  | 从 | 到 | 触发者 | 条件 |
  | --- | --- | --- | --- |
  | `public` | `private` | 作者 | **任意时间**（不受 24 小时编辑窗口限制） |
  | `private` | `public` | 作者 | **任意时间**（同上） |

- **`status` 流转（两条轴里的「平台轴」）**：

  | 从 | 到 | 触发者 | 条件 |
  | --- | --- | --- | --- |
  | （新建） | `normal` | 系统 | 发布成功，默认态 |
  | `normal` | `pending` | 系统 | 被 ≥5 名不同用户举报，或命中疑似敏感词 |
  | `normal` | `pending` | 管理员 | 人工置入待审 |
  | `pending` | `normal` | 管理员 | 复核通过，可见性按作者原本的设置还原 |
  | `pending` | `hidden` | 管理员 | 确认违规 |
  | `normal` | `hidden` | 管理员 | 直接判定违规（不经待审） |
  | `hidden` | `normal` | 管理员 | 申诉通过或误判恢复 |
  | `normal` / `pending` / `hidden` | `deleted` | 作者 | 任意时间主动删除 |
  | 任意 | `deleted` | 管理员 | 严重违规强制移除 |

  两条轴互不干扰：一条内容可以同时是「仅自己可见（`private`）+ 审核中（`pending`）」，
  作者改可见性不会影响审核状态，管理员改审核状态也不会覆盖作者的可见性设置。

- **硬性规则**：
  1. **所有公开查询必须统一走一个过滤入口**（如 `visible_posts_query(...)`），禁止各接口自己拼 `WHERE`。
     时间线、搜索、随机漫步、标签筛选、作者主页、收藏、通知、分享卡片全部复用这个入口。
  2. **只有 `normal` + `public` 的内容会出现在任何公开位置**；`pending` / `hidden` / `deleted` / `private` 一律不出现在公开列表。
  3. 非作者访问 `pending` / `hidden` / `deleted` 的详情接口，一律返回 **404**（不暴露存在性）。
  4. **每次状态变化都要留痕**：写入 `post_status_history`（原状态、新状态、原因、操作者类型与 ID、时间）。
  5. 状态变化给作者产生一条站内通知，说明变化与原因；「已隐藏」附申诉入口。
  6. 幂等：重复把状态设为同值，不产生新记录、不重复通知。
  7. 已删除为软删除，30 天内在「回收站」可恢复，超期物理清理。
  8. 自动待审只做「暂时不可见」，不做删除，管理员可一键恢复。
  9. **内容编辑与可见性调整是两件事，窗口不同**：内容编辑限发布后 24 小时内；可见性（`visibility`）**随时可改**，
     不受该窗口约束。接口也要分开（编辑内容走 `PATCH /api/posts/{id}`，改可见性走 `PATCH /api/posts/{id}/visibility`），
     避免用一个接口把两种权限混在一起。

- **验收**：
  - 作者在个人画布能看到每条创作的当前状态徽标，5 种状态都能正确显示。
  - 后台把一条创作设为 `pending` 后，其他用户的时间线、搜索、随机漫步、作者主页同时消失（5 个入口一致）。
  - 非作者请求 `pending` 内容详情，返回 404。
  - 同一条创作先 `pending` 再恢复 `normal`，状态历史里有完整两条记录，且可见性还原为原来的 `public` / `private`。
  - 作者删除后，自己的回收站可见并可恢复；其他用户与作者的新列表里都看不到。
  - 对同一状态重复设置 3 次，`post_status_history` 只记录 1 次变化。

### 8.3 索引要求

- `daily_posts(post_date DESC, id DESC)`：时间线分页
- `daily_posts(status, post_date DESC)`：按状态过滤（公开列表统一入口依赖它）
- `daily_posts(user_id, post_date DESC)`：个人画布
- `likes(post_id)`、`comments(post_id)`、`favorites(post_id)`：计数与列表
- `notifications(user_id, is_read, created_at DESC)`：未读通知
- 若启用搜索：`daily_posts` 上建 `tsvector` GIN 索引

### 8.4 迁移方式

使用 Alembic 管理迁移（当前项目用 `Base.metadata.create_all` 直接建表，无法安全演进线上库）。
V1.1 第一步即引入 Alembic，并补齐首次基线迁移。

## 12. 验收与测试要点

| 类别 | 用例 |
| --- | --- |
| 隐私 | 未登录请求时间线与详情接口，断言响应中不含 `email` |
| 时间 | 以 Asia/Shanghai 为准，验证 00:30 / 08:30 / 23:30 三个时刻的发布归属日期 |
| 并发 | 同一用户并发 10 次发布，仅 1 条落库 |
| 权限 | 他人编辑/删除/查看私密内容均返回 403 或 404 |
| 私密 | A 发私密创作后，B 在时间线/搜索/随机漫步/作者主页均不可见；B 直接访问 id 返回 404；B 点赞评论收藏不产生数据 |
| 私密计数 | 私密创作计入作者本人累计创作与连续发布天数，但不进入任何公开统计 |
| 一天一条 | 同一天先发私密再发公开被拒绝；先发公开再发私密同样被拒绝 |
| 举报去重 | 同一用户重复举报同一内容被拒，不产生重复记录；第 5 个不同用户举报时内容自动进入待审 |
| 拉黑隔离 | A 拉黑 B 后双向不可见、不可互动、无通知；B 访问 A 主页返回 404；解除后立即恢复 |
| 拉黑幂等 | 重复拉黑 / 重复解除均成功，`blocks` 表不产生重复记录 |
| 拉黑过滤一致性 | 时间线、搜索、随机漫步、作者主页、收藏五个入口的过滤结果一致 |
| 状态徽标 | 作者侧 5 种状态（正常 / 仅自己可见 / 审核中 / 已隐藏 / 已删除）均能正确显示 |
| 状态与公开入口 | 把一条创作设为 `pending` 后，5 个公开入口同时不可见；非作者请求详情返回 404 |
| 状态留痕 | 状态每次变化都写入 `post_status_history`，重复设同值不产生新记录 |
| 状态恢复 | `pending` → `normal` 恢复后，可见性还原为作者原本的 `public` / `private` |
| 可见性无时限 | 发布 3 天后仍可切换公开 / 仅自己可见；同一时刻改内容被拒（超 24 小时）但改可见性成功 |
| 翻页 | 60 条数据下滚动到底，无重复无遗漏 |
| 更新 | 校验和不匹配时不调起安装；已忽略版本不再提示 |
| 降级 | 断网打开关于页，产品介绍、使用引导、隐私文档均可读 |
| 自愈 | 手动停掉隧道，10 分钟内服务状态恢复正常且 App 可登录 |
| 兼容 | Android 8 / 12 / 15 真机各一台冒烟 |

## 13. 风险与待确认问题

### 13.1 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 临时隧道地址漂移 | Cloudflare Quick Tunnel 非稳定域名，地址会变 | 短期靠常驻看门狗；中期建议换成固定域名 + 命名隧道 |
| 图片存储成本 | 配图会显著增加存储与带宽 | 服务端压缩 + 缩略图 + 单条上限 3 张 |
| 引入 Alembic 的迁移风险 | 线上已有数据，需要基线对齐 | 先在本地与测试库演练，确认基线后再上线 |
| 关于页内容维护成本 | 产品介绍、协议文档需要持续更新 | 文案集中在 `config` 与 `docs` 中管理，避免散落 |
| 通知功能引发新依赖 | 站内通知需要额外的轮询或推送 | V1.2 先做站内拉取，推送留到 V2.0 |
| 举报被滥用 | 恶意举报可让正常内容被动隐藏（≥5 人举报即待审） | 同内容每人只能举报一次 + 24 小时上限；待审只做「暂时不可见」而非删除；后台可一键恢复；记录恶意举报账号 |
| 拉黑被滥用 | 用户可能批量拉黑造成对方无法互动 | 拉黑上限 1000；拉黑只影响双方之间的可见性与互动，不影响被拉黑者对其他人的正常使用 |
| 处置误判 | 人工判断可能出错 | 处置留痕（`moderation_actions`）+ 作者申诉入口 + 可回滚（隐藏可恢复） |

### 13.2 已确认决策（2026-11-06 产品负责人确认）

| 编号 | 决策项 | 结论 | 落地位置 |
| --- | --- | --- | --- |
| D1 | 每日发布条数 | **严格保持每天只能发一条**，任何情况下不放开 | FR-1、FR-0.3 |
| D2 | 补写窗口 | **固定 3 天**，可补写最近 3 天内任意一天 | FR-1 |
| D3 | 编辑窗口 | **固定 24 小时**，超过仅可删除 | FR-2 |
| D4 | 私密创作 | **支持「仅自己可见」**，纳入 V1.1 | FR-20 |
| D5 | 反馈方式 | **接服务端工单后台**（工单 + 回复 + 状态流转） | FR-15、8.2、9.2 |
| D6 | 尝鲜版更新通道 | **待定** | FR-13 |
| D7 | 内容安全 | **必须支持举报与拉黑**，防止不健康内容传播 | FR-17、FR-21 |

| D9 | 可见性窗口 | **内容编辑限 24 小时内，可见性随时可改**（两者分开） | FR-2、FR-20、FR-23 |

### 13.3 已确认 / 仍待确认

1. **[已确认] 关于页的「尝鲜版更新通道」：暂不做。**

2. **[仍待确认] 站内通知**：状态变化通知（被举报待审 / 被隐藏）本期先用
