### 结论

主流程（注册 → 登录 → 发布 → 浏览 → 个人中心）**能跑通**，这一点已用真实接口验证。
但通盘看下来，**有 13 条流程不闭环**（6 条是功能缺失，7 条是现有链路断点），其中 3 条会让用户卡死或看不懂，另有 1 个**致命安全逻辑问题**。

用户已确认的一条关键规则：**内容编辑限发布后 24 小时，可见性（公开 / 仅自己可见）随时可改。**
这两件事必须做成两条独立流程，不能共用一个时间窗口。

按严重度排序，必须先处理的三件事：

1. **默认密钥可伪造任意用户身份**（已实测，可直接 impersonate 任何账号）
2. **登录失败时页面整页重载，错误提示一闪就没**
3. **隧道自愈后，已经打开的 App 不会跟着恢复，只能重启**

## 2. 什么叫「闭环」

一条流程要算闭环，必须同时满足五个条件。本文档就按这五条逐项判定：

| 编号 | 条件 | 说明 |
| --- | --- | --- |
| C1 | 有入口 | 用户能自然进入，不需要猜地址 |
| C2 | 有出口 | 成功后到达明确终点，有反馈 |
| C3 | 失败可恢复 | 出错时给出可执行的动作，而不是死胡同 |
| C4 | 状态可恢复 | 刷新、重启、网络中断后不会丢状态 |
| C5 | 服务端也守规则 | 规则同时在数据库/接口层成立，不只靠前端挡 |

## 3. 端到端实测结果

在本地栈上用临时账号跑了一遍完整链路（测试数据已清理，库已恢复为 3 用户 / 3 创作）：

| 步骤 | 结果 | 判定 |
| --- | --- | --- |
| 注册 | `201` | 通 |
| 登录 | `200`，拿到 token | 通 |
| 取当前用户 `/auth/me` | `200` | 通 |
| 发布创作（带心情） | `201` | 通 |
| 同一天再次发布 | `400`「今天已经发布过创作了」 | 规则生效 |
| 发布时给非法心情 | `400`「今天已经发布过创作了」 | **错误优先级错**（当天已发时永远测不出心情非法） |
| 公开时间线 | `200`，总数 4 | 通 |
| 公开接口返回的作者字段 | `created_at` / **`email`** / `id` / `username` | **泄露隐私** |
| 我的创作 | `200`，总数 1 | 通 |
| 不带 token 访问受保护接口 | `403`「Not authenticated」 | **与 401 不一致** |

安全验证：使用默认密钥 `your-secret-key-change-in-production` 手工构造 `sub=1` 的 JWT，
访问 `/api/auth/me` 返回 **`200`**，并直接拿到用户 1 的完整资料。**该漏洞已确认可利用。**

时区验证：

| 输入 | 北京日期 | 后端判定日期 | 结果 |
| --- | --- | --- | --- |
| `created_at = 2026-11-06 17:00:00+00`（即北京 11-07 01:00） | `2026-11-07` | `2026-11-06` | **判定错位** |

数据库 `TimeZone = UTC`，而代码用 `date.today()` 与 `date(created_at)`，两者都在 UTC 上算。

## 4. 流程闭环清单

### 4.1 账号域

| 编号 | 流程 | 现状 | 断在哪 | 结论 |
| --- | --- | --- | --- | --- |
| F1 | 注册 → 自动登录 → 首页 | 注册成功后内部再调一次登录，成功即进首页 | **注册成功但自动登录失败时**，提示的是「注册失败」，而账号其实已经建好了；用户重试会被告知「邮箱已被注册」，从此卡死 | ⚠️ |
| F2 | 登录 → 首页 | 输错密码时后端返回 401 | 前端拦截器收到 401 就无条件 `window.location.href = '/login'`，而用户**此刻就在 /login**，于是整页重载，`setErrorMessage` 刚设的提示被刷掉 | ❌ |

#### 4.7.1 冻结项的修复意见（按建议顺序）

**① F14 内容编辑与删除（✅ 2026-11-06 已交付）**

- 内容编辑：后端已经返回 `can_edit_content`（发布后 24 小时窗口）。新增 `PATCH /api/posts/{id}` 只允许改 `content` 与 `mood`，超窗返回 409、非作者 403；写入 `edited_at`，详情页显示「已编辑」。
- 删除与恢复：复用现有 `status` 轴，`DELETE /api/posts/{id}` 置 `deleted`，`POST /api/posts/{id}/restore` 恢复；个人中心加「回收站」，30 天内可恢复；删除**不释放当天名额**，与「严格每天一条」保持一致。
- 关键约束：内容编辑（24 小时窗口）与可见性切换（随时可改）保持两条独立通道，不要合并成一个「编辑」开关——这是之前已经确认过的产品决策。

**② F13 草稿与补写（✅ 本地草稿 + 补写 3 天已交付）**

- 第一步零后端改动：发布页把内容、情绪、日期写进 `localStorage`，刷新、断网、误关都能恢复。
- 第二步再做服务端草稿表 `post_drafts(user_id, post_date, content, mood, updated_at)`，支持跨设备继续写；补写窗口用 `post_date` 判定 3 天，第 4 天返回明确原因而不是笼统报错。

**③ F20 搜索 / 标签 / 作者主页（先做作者主页）**

- 作者主页 `/u/:username`：`PublicUserResponse` 与「按作者取创作」的公开查询已经具备，主要是前端路由与入口，顺带把详情页作者名变成可点。
- 搜索：新增 `GET /api/posts?q=`，用 `ILIKE` 做前缀匹配，必须组合进 `content_safety.public_posts_query`，否则会把私密/待审内容搜出来。
- 标签：需要先有标签模型与写入规则，建议排在搜索之后。

**④ F8 忘记密码（依赖外部通道）**

- 没有邮件通道前：先做「账号申诉」入口（提交邮箱 → 生成后台工单 → 人工重置），直接复用现有 staff 后台与工单模型。
- 有 SMTP 之后：`POST /api/auth/password/forgot` 发验证码（15 分钟有效、单账号 1 分钟 1 条、单日 10 条上限），`POST /api/auth/password/reset` 校验后改密，并**撤销该用户全部 refresh token**，避免旧会话残留。

**⑤ F28 残余风险（已缓解，可继续加固）**

- 现状：隧道地址变化后，最多一次请求失败即会重新解析；用户也可以到关于页点「重新获取地址」立刻恢复。
- 进一步做法：App 回到前台或网络恢复时（`online` 事件）后台静默探测一次健康检查，把「一次失败」也省掉。

#### 4.7.2 本轮 UI 实测发现的两个小建议（未擅自改，等你确认）

1. **举报弹层里「同时拉黑该作者」默认是勾选状态。** 实测一个只想举报的用户，如果不留意这个勾选项，提交后会静默把作者加入黑名单，导致对方内容从他的时间线消失，用户可能不知道为什么少了内容。建议默认不勾选，或把勾选项放到提交按钮下方并明确提示「勾选后你将不再看到该作者的内容」。
2. **举报弹层在提交前不记住理由选择的可视反馈很弱。** 理由按钮被选中后缺少明显的高亮态确认，用户会怀疑自己有没有点上；建议给选中理由加深色边框或底色（提交按钮可保持禁用直到选中理由）。

### 5.2 S0 级

| 编号 | 问题 | 证据 | 影响 | 对应闭环条件 |
| --- | --- | --- | --- | --- |
| S0-1 | **默认密钥可伪造任意用户身份** | `docker-compose.yml:29` 与 `backend/app/config.py:16` 都使用 `your-secret-key-change-in-production`；实测用该密钥构造 `sub=1` 的 HS256 JWT，访问 `/api/auth/me` 返回 `200` 并拿到用户 1 的资料 | 攻击者改一个数字就能冒充任何用户。后续一旦上线编辑、删除、私密内容，危害会从「读到公开邮箱」升级为「替别人删内容、看私密创作」 | C5 |

3. 增加回归测试：默认密钥启动必须失败，伪造 `sub` 的 token 必须返回 `401`，而不是 `200`。

| P1-6 | **注册已成功却提示注册失败** | `RegisterPage.tsx` 把注册和自动登录放在同一个 `try`；登录失败统一提示「注册失败」 | 用户以为没注册成功，重试时被告知邮箱已存在，账号与提示互相矛盾（对应 F1） |
| P1-7 | **列表没有翻页出口** | `HomePage.tsx` 只请求 `page=1&limit=20`；`ProfilePage.tsx` 只请求 `limit=50` | 第 21 条、第 51 条以后永远访问不到；内容越多越严重（对应 F15、F18） |
| P1-8 | **详情接口存在，但前端没有详情页** | 后端有 `GET /posts/{id}`；`App.tsx` 没有 `/post/:id` 路由 | 分享、从列表点进单条都无处可去，后端接口是死接口（对应 F16） |
| P1-9 | **随机漫步的空状态文案与事实不符** | `ExplorePage` 初始 `enabled: false`，未点按钮时列表为空，却显示「还没有人发布创作」 | 库里明明有内容，用户却以为产品是空的，属于误导（对应 F17） |
| P1-10 | **网页版仍渲染原生更新按钮** | `AboutPage.tsx` 在非原生环境仍显示「立即更新」；`useAppUpdate` 没有原生插件时直接 `return` | 用户点击后没有反馈或抛错，页面底部却提示「请在 Android App 内操作」（对应 F24） |
| P1-11 | **隧道切换后已打开的 App 不会恢复** | `runtimeConfig.ts` 用 `resolvedRuntimeConfigPromise` 永久 memoize，没有失效机制 | 隧道地址变了，App 仍然打旧地址，只能重启；与运维域「自愈」能力不闭环（对应 F28） |
| P1-12 | **网络错误没有可执行出口** | 页面统一展示 `error.message`（通常是 `Network Error`），没有重试按钮，也不区分断网、服务器不可达、登录过期 | 用户无法判断是自己没网还是产品坏了，只能反复点或放弃（对应 F29） |
| P1-13 | **同一天重复发布被拒后没有下一步** | 发布接口返回 400，但页面没有「查看今天那条 / 去修改」的入口 | 用户写完才被告知不能发，且今天那条在哪里也不知道（对应 F10） |
| P1-14 | **发布成功后没有「看刚发的那条」** | 成功后提示 1.5 秒回首页 | 用户无法确认自己写的内容是否完整保存，也找不到刚才那条（对应 F9） |

### 5.5 P2 级

| 编号 | 问题 | 证据/位置 | 影响 |
| --- | --- | --- | --- |
| P2-1 | **错误优先级颠倒** | `posts.py` 先查「今天是否已发」，再校验心情标签；当天已发的用户永远看不到「无效的情绪标签」 | 调试和提示都失真，用户不知道真正错在哪 |
| P2-2 | **心情用名称字符串关联，没有外键** | `DailyPost.mood = Column(String(20))`；查心情靠 `get_mood_by_name` | 心情改名或删除后，历史创作直接丢失心情关联；后续做筛选、统计都会断链 |
| P2-3 | **随机漫步可能重复，且没有排除条件** | `get_random_post` 只有 `ORDER BY random()` | 用户可能连续看到同一条；发完自己的内容也可能随机到自己；体验上像没有新内容 |
| P2-4 | **未登录与无效 token 返回不一致** | 不带 token 返回 `403 Not authenticated`，无效 token 返回 `401` | 前端难以用统一规则处理；以后接入更多客户端时容易踩坑 |
| P2-5 | **分页计数与列表不是同一快照** | 总数和列表分两次查询，中间可能插入新数据 | 并发发布时 `total` 与 `items` 可能不一致，页码边界会抖动 |
| P2-6 | **登录与注册没有限流** | 注册、登录接口无频率限制 | 暴力破解和批量注册成本低，配合默认密钥漏洞会放大风险 |

## 6. 闭环目标设计

以下不是新增功能清单，而是「这条流程到哪一步才算真正结束」的判定标准。每条都对应第 2 节的 C1–C5。

### 6.1 账号域闭环

目标链路：

```text
注册 → 账号创建成功 → 自动登录 → 首页
  └─ 自动登录失败 → 提示「账号已创建，请用邮箱登录」 → 手机号/邮箱预填 → 登录
登录 → 首页
  └─ 失败 → 区分密码错误 / 账号不存在 / 网络不可达 → 原页保留错误 → 可重试
Token 过期 → 保留 returnTo → 登录 → 回到原页面
忘记密码 → 输入邮箱 → 发重置凭证 → 设新密码 → 登录
```

闭环判定：

| 条件 | 目标 |
| --- | --- |
| C1 入口 | 登录页、注册页、忘记密码入口都在场，不需要猜 |
| C2 出口 | 登录/注册成功后进入明确目标页，不再闪屏 |
| C3 失败可恢复 | 密码错、网络错、账号已存在三种提示可区分，且都能留在原表单重试 |
| C4 状态可恢复 | 冷启动验证期间不误判未登录；token 过期后能回到原页面 |
| C5 服务端守规则 | 密码错误返回 401 但不触发全局跳转；限流生效；默认密钥拒绝启动 |

### 6.2 创作域闭环

目标链路：

```text
选择日期（今天 / 补写最近 3 天）→ 写内容 → 本地草稿自动保存
  → 提交 → 服务端唯一约束校验 → 成功 → 跳到刚发布的那条 → 可编辑 / 改可见性 / 删除
  └─ 同一天已有内容 → 提示「这一天已经写过」→ 提供「查看/编辑那一天」入口

发布后 24 小时内：可以改内容，显示「已编辑」
发布 24 小时后：改内容被拒，但仍可删除
任意时间：可以在「公开 / 仅自己可见」之间切换
删除后 30 天内：可恢复；其他用户立即不可见
```

闭环判定：

| 条件 | 目标 |
| --- | --- |
| C1 入口 | 首页、个人中心、补写日期都有明确入口；同一天重复发布在前端先提示 |
| C2 出口 | 发布成功有单条详情页；编辑成功有「已编辑」标记；可见性切换立即生效 |
| C3 失败可恢复 | 内容编辑超时给出「可删除」出口；可见性切换失败可重试；断网草稿不丢 |
| C4 状态可恢复 | 草稿、日期选择、编辑内容在刷新或重启后不丢 |
| C5 服务端守规则 | `post_date` 按 `Asia/Shanghai` 计算；`UNIQUE(user_id, post_date)` 在数据库生效；编辑接口和可见性接口分别校验 |

> 这条闭环的重点不是「加一个开关」，而是把**内容**和**可见性**拆成两条独立状态：
> 内容有 24 小时窗口，可见性没有窗口。两者都不应依赖前端 `canEdit` 一个布尔值。

### 6.3 浏览域闭环

目标链路：

```text
时间线 / 随机漫步 / 搜索 / 标签筛选 / 作者主页
  → 列表有明确空状态 → 可加载更多 → 点进详情 → 返回原位置

公开内容：所有人可见
私密内容：仅作者可见，其他入口一律不出现，直接访问 id 返回 404
自己的内容：在个人画布中与公开内容混排，但带「仅自己可见」标记
```

闭环判定：

| 条件 | 目标 |
| --- | --- |
| C1 入口 | 首页、随机、搜索、标签、作者主页都有明确入口；空状态只在真的为空时出现 |
| C2 出口 | 列表可翻页/加载更多；详情页可返回且保留列表位置 |
| C3 失败可恢复 | 列表请求失败显示重试；详情被删除/隐藏时显示明确说明 |
| C4 状态可恢复 | 返回列表后不丢页码和滚动位置；刷新后可继续浏览 |
| C5 服务端守规则 | 公开列表只返回 `normal + public`；私密、审核中、已隐藏、已删除内容不出现在任何公开入口 |

### 6.4 更新域闭环

目标链路：

```text
进入关于页 → 自动检查 → 有新版本 → 展示版本说明
  → 下载（进度 / 取消）→ 下载完成 → 校验 SHA-256
  → 调起系统安装器 → 授权 → 安装成功
  └─ 用户取消安装 / 重启 App → 保留「继续安装」入口 → 不重复下载
  └─ 签名不一致 / 下载失败 → 明确错误 → 返回检查或提供手动下载

网页版：不显示原生安装按钮，只说明「请在 Android App 内更新」
```

闭环判定：

| 条件 | 目标 |
| --- | --- |
| C1 入口 | 关于页有版本、更新说明和检查入口 |
| C2 出口 | 安装成功或明确失败，不长时间停在「已调起安装」 |
| C3 失败可恢复 | 取消安装、下载失败、签名不一致都有对应下一步 |
| C4 状态可恢复 | App 重启后仍能找到已下载的安装包并继续安装 |
| C5 服务端守规则 | 清单版本、包名、SHA-256、签名证书一致才允许更新；网页端不误导用户 |

### 6.5 网络与运维域闭环

目标链路：

```text
App 启动 → 读取运行时配置 → 请求健康检查 → 正常则进入业务
  └─ 配置不可达 → 使用缓存 → 提示「当前使用缓存地址」→ 可手动重试
  └─ 隧道切换 → 已打开的 App 下次请求重新解析地址 → 无需重启
  └─ 请求失败 → 区分断网 / 服务不可达 / 登录过期 → 给出重试或重新登录
```

闭环判定：

| 条件 | 目标 |
| --- | --- |
| C1 入口 | 关于页提供网络/服务地址自查信息 |
| C2 出口 | 恢复后页面能继续原操作，而不是要求重启 |
| C3 失败可恢复 | 所有页面都有「重试」；错误信息说清是哪一类问题 |
| C4 状态可恢复 | 配置缓存可在一定时间后失效或手动刷新；隧道切换后自动恢复 |
| C5 服务端守规则 | 健康检查可区分进程存活与数据库可用；看门狗告警可追踪 |

## 附录：一句话结论

当前项目的主流程能跑通，但**「能跑通」不等于「已闭环」**：
账号域缺失败恢复，创作域缺发布后的生命周期，浏览域缺分页和详情，更新域缺取消与重启恢复，网络域缺配置失效与错误分类。

其中 **P0 默认密钥问题优先级最高**，因为它会让后续所有权限规则失去意义；
其次是 **公开接口泄露 email** 和 **每天一条的时区与唯一约束**，它们直接影响用户信任和产品核心规则。

建议的推进顺序是：先修安全与数据底座，再做创作/浏览闭环，最后收口更新与网络；每批完成后都用本文档的 C1–C5 重新验收一次。
